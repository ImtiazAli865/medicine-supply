# Tasks: Offline Order Taking, Automatic Sync and Backup

**Input**: Design documents from `/specs/009-offline-sync-backup/`
**Prerequisites**: plan.md, spec.md, research.md (decisions D1-D13), data-model.md, contracts/api.openapi.yaml, contracts/backup-file.schema.json, quickstart.md
**Tests**: INCLUDED. Constitution Principles I, IV, V, VII and VIII and spec success criteria SC-001 to SC-010 require them. Within each story write its tests first and confirm they fail for the right reason before the implementation (pure code and integration tests first, then the screens). Nothing offline may be claimed in the app or in a report unless a test that ran offline proves it.
**Organization**: Grouped by user story. Priority order: US1 take an order with no internet (P1), US2 the order reaches the server by itself exactly once (P1), US3 nothing is lost and nothing is silently overwritten (P1), then US4 new stores and unknown medicines offline (P2), US5 backup and restore (P2), US6 sync status in Settings (P2), then cross-cutting polish and owner steps. US1 and US2 together are the minimum that is useful; US3 must be finished before the owner is asked to rely on the module.

- **Wording rules (FR-007, SC-003)**: a change that exists only on the phone says "Saved on this device, not yet sent"; the words "Saved at HH:MM" and "Synced" appear only after the server confirmed. - **Data rules**: IndexedDB holds the device copy and the journal; never use `localStorage` or `sessionStorage` for data (a harmless UI preference only). The device copy holds the slim medicine shape (including the current `selling_price` shown by the editor) and never a purchase price, MRP, cost, margin, profit, balance or invoice value; the backup holds no price at all. Every business has its own database `medsupply-<businessId>`; code must never open a database of another business than the signed-in one.
- **Service worker rules**: `public/sw.js` never caches `/api/` responses or any page HTML except the `/offline` shell, never answers an API request, and holds no business logic. It must not break the online screens when the shell or the asset list is missing.
- **Existing online specs**: with a device copy present, a failed read is answered from the device and labelled. Every existing spec that tests an online failure state calls `blockDeviceStorage(page)` (T019) so it keeps testing exactly what it tested, one new test per kind checks the device-labelled answer, and each changed expectation is listed (T028).

The owner signs in themselves (never ask for or type passwords or the secret key). The browser tests start their own production build on port 3000, so stop `npm run dev` and any server on port 3000 first (ask the owner before stopping a process they started).
