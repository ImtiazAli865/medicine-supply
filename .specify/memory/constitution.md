# Medicine Supply & Order Management Constitution

Source of truth for product scope: `docs/master-prompt.txt` (what to build) and
`docs/negative-prompt.txt` (what must never be done). If this constitution and those
documents conflict, stop and ask the user before proceeding.

## Core Principles

### I. Real Functionality, No Fakes (NON-NEGOTIABLE)
Every feature MUST perform its real operation against the real backend. Code MUST NOT
simulate Supabase saves, show success messages for failed requests, ship buttons or
navigation without a working action, leave critical screens as placeholders, or use
hardcoded lists as the database. Voice, offline, sync, PDF and print MUST NOT be claimed
as working until implemented and tested. Supabase MUST NOT be reported as connected
until valid configuration and a successful integration test exist. A feature that cannot
be completed MUST be reported as a limitation, never replaced silently by a stub.

### II. Billing Integrity and Price Snapshots (NON-NEGOTIABLE)
- Money MUST be PostgreSQL `NUMERIC` and handled decimal-safe end to end. Currency is PKR.
- A price snapshot (purchase, selling, MRP) is taken at order CONFIRM. Invoice totals MUST
  use the order line's snapshot, never the current catalog price.
- A line with no Selling Price at confirm stays unpriced (pending). It receives its
  snapshot only through the Pending Prices flow, only after the user confirms, and the
  change MUST be recorded in the audit history. A line that already has a snapshot MUST
  NEVER change.
- Selling Prices MUST NEVER be invented. An invoice MUST NOT be issued while any line
  lacks a verified Selling Price.
- Order lines carry a delivered quantity that defaults to the ordered quantity. Invoices
  use the delivered quantity. Ordered, purchased, delivered and sold quantities are
  distinct and MUST NOT be conflated.
- Invoice status is stored only as draft, issued or cancelled. Unpaid, partially paid and
  paid are derived from ledger allocation, never stored.
- Issued invoices and their Account Summary snapshot (previous balance, this invoice,
  payment received, balance due) are immutable. Corrections use cancellation with a
  reversal or a replacement invoice.
- Invoice numbers are generated by a controlled server-side mechanism. Retries, refreshes
  and double taps MUST NOT create duplicate invoices or numbers.
- Customer invoices, the Account Summary and the Store Statement MUST show only
  permitted fields and MUST NEVER show purchase price, MRP, cost, margin or profit.
- Profit uses the weighted average of actual recorded purchase costs. Until a purchase is
  recorded, profit MUST be labelled an estimate/incomplete. Internal reports are never
  part of customer printouts.

### III. Ledger (Khata) Is Append-Only
- A store's balance MUST be computed from ledger entries and never stored as an editable
  number. Entry types: opening_balance, invoice, payment, adjustment, reversal.
- Entries MUST NEVER be edited or deleted. Errors are fixed by a reversal plus a corrected
  entry with a reason, both audited.
- Only issued invoices create ledger entries. Drafts never do.
- Payments belong to the store account, are allocated oldest-unpaid-first, and MUST NEVER
  be applied to another store. Overpayment is kept as an advance and applied to the next
  invoice.
- Every payment carries a client-generated idempotency key so retries, refreshes and sync
  never record it twice. A balance including unsynced payments MUST be shown as
  "pending sync".
- Issuing an invoice with "payment received now" is one atomic database operation.

### IV. Medicine Identification and Order Safety (NON-NEGOTIABLE)
- Different strengths, dosage forms, manufacturers or pack sizes MUST NEVER be merged or
  substituted on name similarity. Aggregation groups by product ID only.
- Unknown medicines and unknown stores MUST never block or lose an order: an unknown
  medicine becomes a pending line keeping its exact name, quantity and unit. Quick
  Register requires only name and unit and MUST NOT invent price, strength, pack size or
  manufacturer. Duplicate checks run before any product is created. Linking pending lines
  to a newly registered product requires user confirmation per link.
- Pending lines never block confirming an order; they only block issuing the invoice.
  They MUST appear in the market list under "Not yet registered".
- One store's items MUST NEVER be mixed into another store's order. Saved orders MUST
  NEVER be overwritten or emptied by refresh, navigation or store change.
- A purchase checkbox is not proof of purchase; actual purchased quantity is recorded.
- The app MUST be fully usable with an empty catalog and no stores. Every list screen
  needs an empty state naming the next action.

### V. Security, RLS and Secrets (NON-NEGOTIABLE)
- Use is solo (one user per business), but every business table MUST carry `business_id`
  and have Row Level Security enabled and tested from the first migration. RLS MUST NEVER
  be disabled to make something work.
- Login is Supabase email and password. Auth expiry, permission errors and failed requests
  MUST be handled visibly.
- Financial and security-sensitive validation MUST be enforced server-side (constraints,
  RPC/transactions), never by client code alone. Atomic operations use database functions
  or transactions.
- The Supabase service-role key, `GEMINI_API_KEY` and any cloud credentials live only in
  server-side environment variables. Real credentials and `.env` files MUST NEVER be
  committed; `.env.example` holds placeholder names only.
- Important financial changes are written to an audit history.

### VI. Server-Side AI With Human Confirmation
- Gemini is called only from server-side code, behind a `TextToOrderParser` interface.
  The model name comes from `GEMINI_MODEL` and MUST NOT be hardcoded. Speech-to-text sits
  behind its own provider interface; browser Speech Recognition is the default.
- Only the transcript text is sent. Prices, MRP, balances, invoices and other financial
  data MUST NEVER be sent to the provider.
- Output MUST be schema-validated on the server; invalid output is rejected and never
  saved. The AI never chooses the final product, store or price: application code
  matches, and the supplier confirms every transcript and parsed preview before saving.
- A failed, slow or rate-limited (HTTP 429) AI call MUST NEVER block order taking;
  manual entry always remains available. Failures and low-confidence results go to a
  diagnostic log that never contains secrets.
- Real business data requires the paid Gemini tier. Automated tests MUST use a mocked
  provider and MUST NEVER call the real API. Offline speech recognition MUST NOT be
  claimed unless the engine supports it.

### VII. Offline-First With Honest Sync
- IndexedDB holds cached catalog and stores, offline orders, drafts, payments and the
  pending-operation queue. LocalStorage is for lightweight preferences only and is never
  a data backend.
- Order taking, drafts and payment recording MUST work offline. Issuing an invoice
  REQUIRES a connection, so invoice numbers and the ledger snapshot are exact.
- Records use client-generated UUIDs and idempotency keys. Sync MUST detect conflicts,
  MUST NOT overwrite newer server data with stale local data, and MUST NOT delete
  unsynced offline orders without explicit user confirmation.
- The UI MUST distinguish "Saved on this device" from "Synced to server" and never mark
  data synced before the server confirms.

### VIII. Mobile-First, Verifiable Delivery
- UI is mobile-first (Android), English, with large touch targets, readable type,
  searchable dropdowns, and loading, error, empty and offline states. No desktop-only
  layouts and no animations that slow order entry.
- Printing provides A4 and thermal layouts; thermal paper width defaults to 80 mm and
  MUST be a user setting. Prints MUST NOT include the application chrome.
- TypeScript, lint and build errors MUST NOT be ignored. Schema changes ship as
  version-controlled migrations with RLS. CSV imports preview and validate before commit.
- No test, build or deployment result may be claimed unless it was actually run.

## Technical Constraints & Fixed Decisions

- Stack: Next.js App Router + TypeScript, React, Tailwind CSS, Lucide React, Supabase
  (Postgres, Auth, RLS, JS client), IndexedDB, browser printing with print styles.
- One Selling Price per product; no batch or expiry tracking; English UI; PKR.
- Product catalog search is debounced, indexed and server-queried to stay fast at
  thousands of products.
- Supabase interactions and the Gemini route handler are the only places holding server
  secrets; client code receives only the public anon configuration.

## Development Workflow & Quality Gates

- Work proceeds module by module; each module is finished, tested and shown before the
  next starts: 001 login, products, stores; 002 setup/import; 003 manual orders;
  004 pending products; 005 market list/purchases; 006 invoices; 007 khata/payments;
  008 voice; 009 offline/sync; 010 reports; 011 hardening. Earlier modules MUST use
  client-generated UUIDs and `business_id` so later modules need no rework.
- Spec Kit flow per module: spec, plan, tasks, implement. Each plan's Constitution Check
  MUST verify Principles I-VIII. A PHR is recorded for every user prompt; ADRs are
  suggested for significant decisions and created only with user consent.
- A module is done only when its tests pass, covering the applicable items of Section 17
  of `docs/master-prompt.txt`, including RLS checks and a mocked AI provider where
  relevant, and lint, type check and build are clean.
- Make the smallest viable change; do not refactor unrelated code. When requirements are
  ambiguous, preserve user data, ask, and never invent critical financial or medicine
  information.

## Governance

This constitution supersedes other practices. If it conflicts with `docs/master-prompt.txt`
or `docs/negative-prompt.txt`, those documents' "never" rules win until the user resolves
the conflict. Amendments require the user's explicit approval, a documented reason and,
where existing data or code is affected, a migration plan; they are recorded with an
updated Sync Impact Report. Versioning is semantic: MAJOR for removed or redefined
principles, MINOR for added principles or materially expanded guidance, PATCH for
clarifications. Every plan and review MUST check compliance with Principles I-VIII, and
any justified deviation is recorded in the plan's Complexity Tracking. Runtime guidance
for the agent lives in `CLAUDE.md`.
