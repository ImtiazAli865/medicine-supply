# ADR-0006: Invoice Issue and Immutability (function-only writes, number only at issue, frozen snapshot, database guards, cancel as a status change)

> **Scope**: One decision cluster made in Module 006 (invoices and printing). The parts were chosen together and would change together: how an invoice is drafted from a confirmed order, how it is issued (number, frozen snapshot, order status), how it is protected from any later change, and how a wrong invoice is cancelled and replaced. It follows the pattern of ADR-0003, ADR-0004 and ADR-0005.

- **Status:** Accepted (the owner asked for this ADR on 2026-11-16)
- **Date:** 2026-11-16
- **Feature:** 006-invoices-printing
- **Related:** ADR-0003 (order write model: function-only writes, select-only tables, versions, price snapshots), ADR-0004 (replay-safe functions; "counts and lists share one definition"), ADR-0005 (append-only entries; here the status is a column because the constitution stores the invoice status as draft, issued or cancelled), ADR-0002 (REST handlers over RLS, client-generated ids).
- **Context:** The supplier delivers a confirmed order and then bills it. An invoice is a financial record, so Module 006 must meet these rules together: an invoice is priced only from the order line selling price snapshot and never from the current catalog price; an invoice is never issued while a billed line has no verified selling price; a retry, a double tap or two devices must never create a second invoice or a second number; an issued invoice must never change, whatever code path runs, including later modules; the delivered (billed) quantity is kept separate from the ordered quantity; no purchase price, MRP, cost, margin or profit may appear on any invoice or order sheet; and one business must never see or change another's rows. A browser that writes the tables, or an "update the invoice row" design, cannot meet these together.

## Decision

1. **Four tables, written only through `SECURITY DEFINER` functions.** `invoices`, `invoice_lines`, `invoice_events` and `invoice_counters`. Signed-in users have `select` only (Row Level Security on every table); `anon` has nothing; `invoice_counters` is not readable by signed-in users. Writes go through six functions (`invoice_create`, `invoice_set_quantities`, `invoice_refresh`, `invoice_discard`, `invoice_issue`, `invoice_cancel`). Each reads the business from `current_business_id()` and filters every statement by it. Composite keys `(business_id, id)` tie every row to one business. Reads are `SECURITY INVOKER`, so Row Level Security still applies to them. The internal write helpers (`invoice_build_lines`, `invoice_recompute_total`) are not executable by signed-in users.
2. **One live invoice per order, enforced by an index.** A partial unique index on `invoices (business_id, order_id) where status in ('draft', 'issued')`. A cancelled invoice is not live, so a replacement can be made. The client creates the invoice id (a UUID) and it is the request id: the same id again returns the stored draft (`replayed`), a different id for an order that already has a live invoice returns that invoice (`existing`, never a second one), and the same id for another order is refused (`request_reused`).
3. **The invoice number is assigned only at issue, from a per-business counter.** `invoice_counters` is updated inside `invoice_issue` (`insert ... on conflict do update ... returning`); the number is stored as an integer with `unique (business_id, invoice_number)` and shown as `INV-` plus six digits. A discarded draft leaves no gap, a refused or failed issue rolls the counter back, and two simultaneous issues get two different increasing numbers. Lock order is fixed (invoice advisory lock, order advisory lock, counter row) to avoid deadlocks.
4. **Issue is one atomic function with a frozen snapshot.** In one transaction `invoice_issue` checks the rules (status draft, order still `confirmed`, draft not stale, at least one billed line, every billed line has a verified selling price, version matches), recomputes every line total and the grand total from the lines (money is `numeric`, summed in SQL), takes the number, copies the business name, phone and address and the store name, contact, phone and address as they are at that moment, sets the invoice date (Pakistan day), the issue time and the issuing user, writes the delivered quantities back to the order lines, moves the order to `fulfilled`, and writes the invoice and order history. A repeat on an issued invoice returns it (`replayed`). A refusal changes nothing and uses no number. Reasons: `version_conflict`, `invoice_not_draft`, `order_not_confirmed`, `order_changed`, `nothing_to_bill`, `not_ready` (with the blocked lines).
5. **Invoice lines carry only what the customer may see, so cost cannot leak by structure.** Lines copy the medicine name, strength, dosage form, pack size, manufacturer, unit, ordered quantity, delivered (billed) quantity and the selling price snapshot. There is **no column for purchase price, MRP or cost** on any invoice table, and the line total is a generated column `delivered_quantity * selling_price`. Order sheets come from price-free functions that select permitted columns by name. Tests list the table columns and scan every returned JSON and print page for forbidden words.
6. **A draft can be stale; an md5 fingerprint detects it.** The draft stores `source_fingerprint`, an `md5` over the order's active line facts that are copied to the invoice (including the price snapshot). `invoice_get` returns `stale: true` when it differs from the current value, `invoice_issue` refuses with `order_changed`, and `invoice_refresh` rebuilds the lines. The order version alone is not enough, because a price fill from Module 004 does not change it.
7. **Immutability is enforced in the database, not only in code.** `invoices_guard` (before update): when the old status is not `draft`, every column must stay the same, except that an `issued` invoice may change to `cancelled` while setting only the cancellation columns, `updated_at` and `version`; a `cancelled` invoice cannot change at all; the invoice number can never change once set; the draft-to-issued step must set the number and the snapshot together. `invoices_no_delete` refuses deleting anything but a draft. `invoice_lines_guard` refuses every insert, update and delete unless the parent invoice is a draft. `invoice_events` is append-only (only `service_role` may delete, for test cleanup, like the other history tables). Any future module that tries to edit an issued invoice fails at the database.
8. **Cancel is a controlled status change with a required reason.** `invoice_cancel(p_id, p_reason)`: only an issued invoice; a reason of 1 to 500 characters; status becomes `cancelled` with `cancelled_at`, `cancelled_by` and `cancel_reason`; the number, lines and amounts stay untouched; the order returns to `confirmed` and its line delivered quantities return to the ordered quantities; a repeat returns the first cancellation and keeps the first reason. A cancelled number is never reused; the replacement gets the next number. There is no undo; a new draft is made instead.
9. **The order status moves only through the invoice functions.** Migration `0007` changes three Module 003 objects and nothing else: `orders_guard` allows `confirmed -> fulfilled` and `fulfilled -> confirmed`; the `order_events` kind check gains `invoiced` and `invoice_cancelled`; the `order_lines.delivered_quantity` check becomes `>= 0` (a line not delivered is billed at 0). An order with an issued invoice cannot be edited or cancelled until the invoice is cancelled. The market list already counts `confirmed` and `fulfilled`, so it is unchanged by issuing or cancelling (tested).
10. **Counts and lists share one definition.** `invoice_summary` counts the rows of the same internal function `invoice_todo_rows()` that `invoice_todo` returns, so the Home card and the "To invoice" tab cannot disagree.

## Consequences

### Positive

- No code path can change an issued invoice: every forbidden update, line change and delete is refused by the database (tested on PGlite and through the real API), and the only allowed change is issued to cancelled with a reason.
- A lost response, a double tap, a refresh or simultaneous requests give one invoice and one number (tested against the real test project: 10 simultaneous creates give one draft, 10 simultaneous issues give one number and nine replays, 10 different drafts issued at once get the numbers 1 to 10 with no gap and no duplicate, 10 simultaneous cancels give one cancellation).
- Cost cannot appear on an invoice, because no such column exists on any invoice table; the check is structural and is also tested on every output.
- Billing always uses the order line snapshot; changing a medicine price afterwards cannot change an issued invoice (tested, and the owner reported the reprint after a price change on a phone).
- Business isolation is enforced in the functions and by Row Level Security, tested with two real users and crafted ids; a refusal looks exactly like a missing id.
- Measured on the test project (five runs, including the network round trip, maximum): the first page of 1,000 invoices 741 ms (goal 3,000 ms), creating a 20-line draft 316 ms and issuing a 60-line invoice 488 ms (goal 2,000 ms). No performance migration was needed.

### Negative

- Rules in SQL again (migration `0007`, about 1,000 lines), so every change is a migration with PGlite and Supabase tests. A missing business filter in a `SECURITY DEFINER` function would be a leak. Mitigation: composite keys, a filter on every statement, two-user tests with crafted ids.
- The status is a column, so its protection depends on the guard triggers. Mitigation: the triggers refuse every other change, and tests try each forbidden change.
- The delivered quantity is written back to the order lines at issue and reset at cancel. After a cancellation a replacement draft starts again from the ordered quantities, so the supplier enters the delivered figures again (the cancelled invoice keeps the real figures). Accepted as a known limitation.
- Stale detection is strict: any change to a copied order line makes the draft stale, even a harmless one, and the supplier refreshes and re-checks the quantities.
- A typed (unregistered) line with delivered quantity 0 on an invoiced order cannot be registered or linked while the order is `fulfilled` (Module 004 refuses it), although the market list still shows it. The supplier cancels the invoice, registers the medicine, then invoices again. Accepted and tested.
- An issued invoice cannot be edited at all, so a wrong invoice takes two steps (cancel with a reason, then a replacement with a new number). This is deliberate and keeps the history honest.
- Issuing needs a connection (constitution VII); there is no offline issuing.
- Printing is checked with print-media emulation and generated PDF text only; no real A4 or 80 mm thermal printer has been tested.

## Alternatives Considered

- **Let the browser write the tables under Row Level Security.** Rejected: it could not enforce the number sequence, the price check, the freeze or the atomic order update.
- **A database sequence for invoice numbers.** Rejected: a rollback leaves gaps, and a sequence is not per business.
- **Assign the number when the draft is created.** Rejected: discarded drafts would leave gaps and numbers would be consumed by invoices that never exist.
- **Check "one live invoice per order" in application code only.** Rejected: a race between two taps would pass; the partial unique index refuses it at the root.
- **Copy the whole order line and hide cost in the screen.** Rejected: one forgotten field would leak cost; with no cost column it cannot.
- **Edit an issued invoice, or delete it, to correct it.** Rejected by the project rules; cancel with a reason and a replacement keep the audit trail.
- **A separate cancellation table (like ADR-0005 voids).** Rejected: a second source of truth for the status; the constitution stores the status as draft, issued or cancelled.
- **Compare the order version to detect a changed order.** Rejected: it misses a price fill or a link; the fingerprint covers every copied fact.
- **Lock the order while a draft exists.** Rejected: it blocks normal order edits, which the spec allows.
- **Write the draft's delivered quantities to the order lines immediately.** Rejected: a discarded draft would leave the order changed. Keeping the delivered quantity only on the invoice was also rejected, because the order would claim "delivered 10" after 8 were delivered.
- **Server-side PDF generation.** Rejected: a new dependency and out of scope; the browser print dialog with print-media CSS is used.
