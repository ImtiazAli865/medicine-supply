# MASTER PROMPT: Medical Supply & Voice-Based Order Management System

## 1. ROLE AND OBJECTIVE

Act as a senior full-stack software engineer, UI/UX designer, database architect, and AI application developer.

Build a complete, production-minded, mobile-first Medical Supply & Order Management Web Application for a pharmaceutical supplier who collects orders from multiple pharmacies, purchases consolidated quantities from a wholesale market, distributes medicines to stores, generates invoices, and tracks profit.

The application must replace handwritten order-taking, manual quantity calculations, repetitive billing, and paper-based market lists.

Do not create merely a static UI, prototype, or mockup. Build functional workflows with a real Supabase backend, persistent data, validation, printing, offline support, and working navigation.

This document is the full product specification. Build it module by module as described in Section 18: finish, test, and show each module before starting the next. A visual mockup and a flow map of the intended screens and workflow are provided separately as the design reference.

## 6. VOICE-BASED ORDER TAKING

This is a core feature, not an optional visual element.

Provide an in-app microphone button on the order-entry screen.

The supplier should be able to say something like:

"Al Madina Medical: Panadol 20 strips, Brufen 10 strips, and cough syrup 5 bottles."

The system must:

1. Capture speech using a supported speech-recognition implementation.
2. Convert speech into text.
3. Recognize the selected store and requested product names.
4. Extract quantities and units.
5. Match product names against the master catalog.
6. Present a structured order preview.
7. Highlight ambiguous products, unknown names, and uncertain quantities.
8. Allow corrections before confirmation.
9. Save the order and its line items.
10. Display clear save and synchronization status.

Design the recognition layer to support Urdu, Roman Urdu, English, and mixed-language speech when the configured recognition provider supports them.

Voice pipeline and AI provider rules:

- Step 1, speech to text: use the browser Speech Recognition by default. Keep a speech-to-text provider interface so that Google Cloud Speech-to-Text (Urdu code ur-PK) can be added later without changing the order screens.
- Step 2, text to structured order: send the transcript to the Google Gemini API from a server-side route only (for example a Next.js route handler). Ask for strict structured JSON output: the store name as spoken, and a list of items, each with the product name as spoken, the quantity, and the unit. Validate the JSON against a schema on the server, reject anything that does not fit, and treat the result as a draft.
- Step 3, matching: the Gemini output never decides which catalog product, store, or price applies. Matching against the catalog is done by application code (normalized and fuzzy search). Uncertain results become "choose one" or pending lines as described in Sections 7A and 8.
- Send only the transcript text to the AI provider. Never send purchase prices, MRP, selling prices, balances, invoices, or other financial data.
- Keep the provider behind an interface (for example a TextToOrderParser) with the Gemini API as the first implementation, so another provider can replace it. Read the model name from an environment variable (GEMINI_MODEL) and never hard-code it.
- Keep GEMINI_API_KEY on the server only, in environment variables, with a placeholder in .env.example. Never expose the key in browser code or committed files.
- Use the paid tier of the Gemini API for real business data. The free tier is for development with test data only, because free-tier inputs may be used by the provider to improve its products.
- Handle rate limits (HTTP 429), timeouts, invalid output, and no internet with a clear message and a retry. The supplier must always be able to fall back to manual entry or device keyboard voice typing without losing the order. Optionally provide a simple rule-based parser as a degraded fallback for clear, simple sentences; it must flag everything it is unsure about.
- Always show the transcript and the parsed preview for correction before saving. AI output is never saved as a final order without the supplier's confirmation.
- Log AI failures and low-confidence results in a diagnostic log, never storing the API key or secrets.

Do not promise universal offline voice recognition. Browser support and network requirements must be detected and communicated honestly.

Provide manual entry and browser keyboard voice typing as fallbacks.

Never silently substitute a similar medicine when a product match is uncertain.

## 7A. FIRST-TIME USE: STARTING WITH AN EMPTY APP

The supplier will start with no medicine list and no store list. The app must be fully usable from the first minute with an empty catalog and no stores. Never require a pre-loaded list before an order can be taken.

- A short, skippable setup checklist: business details and invoice settings; add stores (or add them while taking the first order); optional catalog import. Nothing else is required.
- Inline "Add new store" inside the store selector of the order screen. Only the store name is required; contact details can be added later.
- Quick Register for medicines: only the product name and unit are required. Strength and dosage form are captured when the supplier says them. Manufacturer, pack size, MRP, Purchase Price, and Selling Price are optional at registration and must never be invented.
- The catalog grows from real orders. Every unknown medicine, spoken or typed, becomes a pending order line that keeps the exact name, quantity, and unit. Quick Register then creates the product once, and the pending line is linked to it.
- An order that contains pending lines can still be saved and confirmed. Pending lines never block confirming an order. They only block issuing the invoice until the medicine is registered and its Selling Price is set. Orders are auto-saved as drafts while they are being entered, so nothing is lost mid-order.
- If a spoken or typed name has several possible matches, the supplier must either pick one or choose "None of these, it is a new medicine", which creates a pending line. The supplier is never stuck.
- When the same unregistered name appears in other stores' orders, propose linking those lines to the newly registered product and ask the supplier to confirm each link. Never auto-merge lines with different strengths, dosage forms, or pack sizes.
- Pending (unregistered) lines must still appear in the consolidated market list, in a separate "Not yet registered" group, grouped by the exact typed name with a store-wise breakdown. They are included in the market-list print, marked "unregistered". Once registered they move into the normal grouping.
- A product without a Selling Price cannot appear on an issued invoice. Provide a "Pending Prices" screen that lists every product (and order line) missing a Selling Price. When the supplier enters a price, order lines that had no price get their price snapshot filled only after the supplier confirms, and the change is recorded in the audit history. Lines that already carry a price snapshot are never changed.
- The real Purchase Price is usually known only at the wholesale market, so it is recorded in Purchase Recording as the actual unit cost. Optionally offer to update the product's current Purchase Price from the latest purchase, after confirmation.
- Voice entry with an empty or small catalog must still work: unmatched names become pending lines and are shown for correction. Manual entry remains available.
- Every list screen needs a clear empty state that shows the next action (for example "Add your first store" or "Take your first order").

## 11. AUTOMATIC BILLING AND INVOICE GENERATION

Generate an invoice draft automatically from each store's saved order.

The invoice must be associated with the correct store and order.

The customer-facing invoice must ONLY display:

- Product Name.
- Quantity.
- Selling Price.
- Total Line Amount (Quantity × Selling Price).
- Grand Total at the bottom.

It may additionally display the supplier's business details, invoice number, date, and store details.

OPTIONAL ACCOUNT SUMMARY (store balance on the invoice):

The supplier wants the store's running balance to be printable on the invoice. Provide an "Account Summary" block below the Grand Total. It is shown only when the supplier turns it on, using a checkbox on the invoice print screen with a default in Settings (default off). It shows only: "Balance as on <date>", Previous Balance, This Invoice (the Grand Total), Payment Received (when a payment was recorded at delivery), and Balance Due.

Rules for the Account Summary:

- Previous Balance is the store's ledger balance immediately before this invoice. Balance Due = Previous Balance + This Invoice - Payment Received.
- The figures are a snapshot saved with the invoice when it is issued, so a reprinted issued invoice always shows the same numbers. Payments recorded later do not change it.
- The issue screen has an optional "Payment received now" amount. If entered, issuing the invoice and recording that payment happen together in one atomic database operation, and the payment appears in the summary.
- It appears on both the A4 and the thermal layouts.
- It must never show Purchase Price, MRP, cost, margin, or profit.
- A draft invoice shows a live preview of the summary; the snapshot is taken at issue.

CRITICAL BILLING RULES:

- Never display Purchase Price on the customer invoice.
- Never display MRP on the customer invoice.
- Never display internal gross profit or cost margins on the customer invoice.
- Calculate the line total using the order's verified Selling Price snapshot.
- Calculate the grand total from the invoice lines.
- Validate all monetary values.
- Do not invent prices for unregistered products.
- Do not finalize an invoice with unresolved required product prices.
- Do not create duplicate invoices when the user refreshes or retries an operation.
- Use a controlled invoice-number generation mechanism.
- Preserve issued invoice history.

Generate a clean A4 invoice and a compact thermal receipt layout. The user must be able to choose which layout to print.

The application should support both browser printing and PDF output where implemented.

## 13. STORE LEDGER (KHATA), DELIVERY, PAYMENTS, AND BALANCES

Every store has its own account (khata) that runs continuously from one invoice to the next.

Example: a store receives goods worth 20,000 and pays 15,000 in cash, so its balance is 5,000. On the next delivery of 8,000 the balance becomes 13,000, because the previous 5,000 carries forward. A later payment of 10,000 makes it 3,000.

Ledger design:

- A ledger table keeps one entry per event for each store: business, store, entry date, entry type, debit amount, credit amount, related invoice or payment, note, created by, and an idempotency key.
- Entry types: opening_balance, invoice, payment, adjustment, reversal.
- A debit increases what the store owes (an issued invoice or an opening balance). A credit reduces it (a payment).
- The balance is always calculated from the ledger entries as a running balance. Never store the balance as an editable number.
- Entries are append-only. They are never edited or deleted. A mistake is corrected with a reversal entry and a new correct entry, with a reason, and recorded in the audit history.
- Only ISSUED invoices create ledger entries. Draft invoices do not. Cancelling an issued invoice creates a reversal entry.
- Opening balance: when the supplier starts using the app, each store's previous outstanding amount can be entered once as an opening_balance entry, with a date and a note.
- Advance: if a store pays more than it owes, the excess is kept as an advance (credit balance) and is applied automatically against the next invoice. It is never lost.

Delivery and payment at the store:

- Order statuses are draft, confirmed, fulfilled (delivered), and cancelled. Marking an order delivered leads to issuing its invoice.
- The issue screen has an optional "Payment received now" amount. If entered, issuing the invoice and recording the payment happen together in one atomic operation.
- A payment can also be recorded later from the store account screen.

Payment rules:

- A payment belongs to the store account, not to a single invoice. The system allocates each payment to the oldest unpaid item first (the opening balance, then invoices by date) and shows each invoice's status: unpaid, partially paid, or paid.
- Support cash payments with a date and an optional reference. Keep the data model ready for other methods (bank transfer, mobile wallet) with a payment method field, but only cash is required now.
- Prevent duplicate payment entries with client-generated idempotency keys, so a retried save, refresh, or sync retry never records a payment twice.
- Payments recorded offline are saved on the device first and synchronized later. Until the server confirms them, the balance is shown as "pending sync".
- Never apply a store's payment to another store's invoices.

Screens:

- Store Accounts: all stores with their balances, highest first, and the total receivable.
- Store Account: the balance, a Record Payment action, and the ledger entries with a running balance.
- Record Payment: amount, date, and reference, with a preview of the balance after the payment and how it will be allocated.
- Store Statement: a printable and PDF document for a date range showing the opening balance, every entry, and the closing balance. It is a separate document from the customer invoice.

Neither the Store Statement nor the Store Accounts screens may ever show Purchase Price, MRP, cost, or profit to the customer. Reports show outstanding balances by store, calculated from the ledger.

Preserve an audit history for every financial change.
